- [x] Slice 2: RAG — done, **verified with real Voyage + real Claude**. The 10 demo articles are loaded in `pylon_dummy.db` (`python -m app.knowledge.load_samples`). Built: `app/knowledge/` — `vector.py` (an `Embedding` column type: real `vector(1024)` on Postgres, JSON text on SQLite; vectors are sent/read as text with SQL casts so no driver codec is needed), `chunking.py`, `embeddings.py` (the `Embedder` seam; `VoyageEmbedder` calls Voyage's REST endpoint with `httpx2`, batches, checks the vector size; model `voyage-4`, configurable), `store.py` (`add_article`: chunk -> **mask** -> embed -> save with the embedding model name; `search`: always filtered by organisation + product (+ articles marked `all`), published articles only, same embedding model only; pgvector `<=>` cosine ranking on Postgres, Python ranking on SQLite), `db.py` (creates the `vector` extension and an HNSW index on Postgres), `samples.py` (10 **invented** demo articles across credipay / finsaas / finsaas-lending / all) and `load_samples.py` (idempotent loader; loads them as `published` because the review workflow is Slice 5). New tables `knowledge_articles`, `knowledge_chunks`, `ai_run_events` (append-only run step log: `retrieval`, `retrieval_failed`, `citations`; reused for tool calls in Slice 3). The AI worker now masks the latest customer messages, embeds them as a query, retrieves the top 4 chunks for the issue's product, puts them in a `<knowledge>` block (escaped like the conversation) and asks the model to cite article ids; only ids that were really retrieved are kept (made-up ids are dropped and logged). Retrieval failure (no key, API error, missing tables) never fails the run: the draft is still produced against "(no articles found)" and a `retrieval_failed` event records why. `GET /ai/runs/{id}` now returns the events; the dashboard shows "Knowledge: <titles> (cited)"; `GET /knowledge/articles` and `GET /knowledge/search?q=&product=` let you try retrieval. **Verified:** `pytest` 146 tests pass (chunking, masking before embedding, every search filter, model separation, Voyage request shape/batching/errors against a mocked server, worker retrieval + citation checks + degrade paths, prompt wrapper escaping, snapshot sources, HTTP audit record, loader idempotence). **On Neon (real pgvector 0.8.6):** created only the two knowledge tables, confirmed the `vector(1024)` column and HNSW index, stored vectors, ran the cosine query with all filters (right article first; draft, other product, other org and other embedding model excluded; vectors read back as lists), then dropped those tables (existing tables untouched). **Live Claude (haiku) with retrieved articles and a stand-in embedder:** a loan-disbursement question got a draft using the right article and cited it; a question the articles do not cover got no invented answer, no citations and an escalate recommendation. **Real Voyage (`voyage-4`):** 8 on-topic test questions each ranked the right article first (relevant scores 0.57-0.68; an off-topic question scored <= 0.12). Real Voyage + real Claude (haiku) end to end on a throwaway copy of the DB: a loan-disbursement question retrieved the right article, the draft used it, cited article 7, the stored prompt held no raw phone number. Added `KB_MIN_SCORE` (default 0.3): weaker hits are not shown to the model; calibrated on only ~9 queries, so re-check with more data (neighbours scored up to ~0.42-0.50, which still pass the filter; the model ignored them and cited only the right article). **Rate limits:** without a payment method Voyage allows 3 requests/min and 10K tokens/min; the loader now embeds all new articles in ONE request and waits/retries on 429 (live traffic never waits: it degrades and logs `retrieval_failed`), which also let it finish a partial earlier load. **Not verified:** the full flow in the browser with knowledge, running the app itself against Neon, and behaviour under the rate limit with several tickets in a minute (the 4th ticket in a minute would log retrieval_failed with the 429 until a payment method is added). **Decisions:** the demo works on SQLite (Python ranking) and Postgres/pgvector is the production path; the vector column is fixed at 1024 dimensions (another size means a schema change); articles are not masked in the prompt (company docs), but articles built from customer conversations must be masked when created (Slice 5); `voyage-finance-2` is a finance-specific alternative (1024 dims) worth comparing with `voyage-4` once the key exists; Voyage prices per million tokens (~$0.02-0.12 depending on model) come from third-party listings and should be checked on Voyage's pricing page.

- [x] Slice 3: MCP gateway + mock tools — done, **verified with real Claude (haiku) calling the mock tools**. First step, as agreed: **per-message context** — new table `message_contexts` (tenant, product, customer ref, correlation id for EVERY message that carries them, written by the event bus with a `message.context_recorded` audit row); the AI worker now answers a message with that message's own context (falling back to the issue-level `issue_contexts`), so a customer who switches product mid-conversation gets that product's knowledge and tools, and each run's correlation id is the one of the message it answers. Then: `app/mcp_servers/` — three clearly labelled MOCK MCP servers (Credipay, FinSaaS, FinSaaS Lending) built with the official MCP SDK, fake data, **read-only tools only** (3 each; the tool names are guesses to confirm against the real interfaces), results deliberately contain full account numbers/emails/phones to exercise result masking. `app/mcp_gateway/` — `registry.py` (the configuration: server per product, the **allowlist** of tools per server, **tenant -> products** map; swapping a mock for the real server is an edit here: transport `http` + URL + a bearer-token env var name) and `gateway.py` (`ToolGateway.open(tenant, product)` opens one MCP session per AI run, discovers tools with `list_tools`, exposes only allowlisted ones; per call it checks allowlist + a per-run call budget (default 4), **substitutes masked placeholders in the arguments with the real values server-side** (the model never sees them; `[CARD_n]` is never substituted: card numbers are never sent to any tool), calls with a timeout, **masks the result again** through the same masker, truncates long results, and returns a masked audit detail). Transports: `inprocess` for the mocks (real MCP protocol over in-memory streams, which also avoids Windows subprocess problems under `uvicorn --reload`) and streamable `http` for real servers. The model client (`llm.py`) now runs the tool loop: tool results go back in one user message, thinking blocks are echoed unchanged, tokens are summed over turns, no forced tool use, and after 5 tool rounds the model is told to answer. Every call is audited: `ai_run_events` rows `tools_offered` (what was offered / blocked by the allowlist), `tool_call` (server, tool, masked arguments, masked result, error flag, latency) and `tool_denied` (with the reason), plus `ai.tool_call:<tool>` / `ai.tool_denied:<tool>` rows in `audit_logs`; the dashboard card shows `Tools used: name (ok|error|denied)`. If tools are unavailable (unmapped tenant/product, no context, server down) the run still completes without them and logs `tools_unavailable`. **Verified:** `pytest` 193 tests pass (gateway: allowlist hides and blocks a write tool offered by a server and the server never runs it, tenant mapping, placeholder substitution, card refusal, result and argument masking, budget, timeout, errors, truncation, and a **real MCP server over HTTP**; worker: per-message context, product-scoped tools, a full account-number-to-informed-draft story with nothing raw in prompt, events or audit, denied/errored/budget cases, graceful degradation, snapshot; model client tool loop against a mocked SDK). **Live (haiku, mock tools, throwaway DB copy):** the customer gave an account number -> Claude called `find_loans_by_account` with the placeholder, then `get_disbursement_status` with the loan reference from the first result, and drafted an informed reply (held for bank verification, account ending 6789, escalate); no raw account/email anywhere in the stored record. With no identifier it called no tool and asked for the loan reference; given a prompt-injection asking it to refund and call any tool it had, it called nothing, named the injection in the summary, and only read-only credipay tools existed. **Found while building:** a `+234 ...` phone number can pass the card checksum by chance and was being masked as a card (`+[CARD_n]`), which would have blocked it from tools and from being restored in drafts; international numbers are now matched before cards. **Limits / not verified:** the gateway does not check that the account or loan a tool is asked about belongs to the customer who is writing (the mock data even returns another borrower's name): in production the tools must be authorised per authenticated customer (see docs/v2-context.md); an AI run with tools makes several model turns, so it was ~10-18 s and ~9K input tokens in the live test versus ~5 s without tools; tool names/arguments are mock guesses; the http transport was tested against our own mock over a local port, not a real Credipay/FinSaaS endpoint; the browser flow with tools was not re-run. Test suite time halved by creating the test schema once and clearing rows between tests.
